- (event) Criação da arquitetura iniciada a partir do PRD, adendo e UX final.
- (decision by user) Seguir como o assistente achar melhor; adotado Coaching path leve com recomendações aplicadas e somente ARCHITECTURE-SPINE.md como entregável principal.
- (constraint) Fontes de produto vinculantes: PRD 2026-07-25, addendum 2026-07-25, DESIGN.md final e EXPERIENCE.md final.
- (constraint) A arquitetura deve preservar a UX final: mobile-first, compra como visitante, Área da Cliente por código/link seguro, briefing protegido, aprovação de arte, produto digital imediato e WhatsApp dentro do suporte.
- (constraint) Não existe app de produção no repositório; há protótipo estático em prototype/. Arquitetura tratada como greenfield.
- (version) Stack verificado em fontes oficiais em 2026-07-27: Next.js 16.2.x estável, React 19.2.x, TypeScript 6.x estável/compatível com o starter, Prisma ORM 7.x, Tailwind CSS 4.3.x, Playwright 1.60.x, PostgreSQL 18.x estável, Stripe API 2026-06-24.dahlia, Supabase Postgres/Auth/Storage como plataforma operacional candidata.
- (decision) Paradigma adotado: modular monolith full-stack com módulos de domínio e portas para provedores externos. Binds: all. Prevents: microserviços prematuros, lógica duplicada entre frontend/admin/webhooks e divergência de dados.
- (decision) Next.js App Router + TypeScript será o starter web inicial; Server Actions/API routes chamam serviços de domínio, não acessam provedores externos diretamente. Binds: storefront, Área da Cliente, admin, webhooks. Prevents: regras de negócio espalhadas em componentes.
- (decision) Postgres é a fonte canônica de dados transacionais; Supabase pode fornecer Postgres, Auth e Storage, mas regras de domínio permanecem na aplicação. Binds: pedidos, clientes, catálogo, briefing, arquivos, aprovações, suporte, notificações. Prevents: estado real dividido entre CMS, gateway, storage e planilhas.
- (decision) Pedido é o agregado central; Carrinho, pagamento, briefing, prévias, aprovação, produção, entrega digital, envio físico, fatura, notificações e suporte referenciam order_id. Binds: UJ-1 a UJ-5. Prevents: histórico fragmentado e atendimento sem contexto.
- (decision) Estado comercial do pedido e estado financeiro são separados. Webhooks do provedor de pagamento são autoridade para confirmação; retorno do navegador não libera briefing, produção ou download. Binds: checkout, pagamentos, transferência, produto digital. Prevents: liberação indevida por navegação incompleta ou pagamento pendente.
- (decision) Transições de pedido seguem máquina de estados explícita executada por comandos server-side idempotentes. Binds: Área da Cliente, admin, produção, QA, envio. Prevents: updates livres que pulem aprovação, produção ou estados de exceção.
- (decision) Configuração pré-carrinho é obrigatória para itens personalizados e server-owned para preço/subtotal; miniatura/personagem é adicional compartilhado cobrado uma única vez por pedido/personagem. Binds: carrinho, checkout, convites, lembrancinhas. Prevents: carrinho incompleto e cobrança duplicada.
- (decision) Briefing mestre pós-pagamento por pedido/evento, com seções condicionais por modalidade. Binds: briefing, convites complexos, lembrancinhas, miniatura. Prevents: múltiplos briefings conflitantes para o mesmo evento.
- (decision) Arquivos privados vivem em storage privado com metadados no Postgres e acesso via URLs temporárias/autorizadas. Binds: fotos, referências, prévias, convites finais, produtos digitais prontos e QA. Prevents: vazamento de imagem infantil, links públicos permanentes e acesso entre clientes.
- (decision) Notificações usam outbox transacional; e-mail e WhatsApp são efeitos assíncronos. Área da Cliente é o registro principal. Binds: briefing, prévia pronta, aprovação, entrega digital, rastreio, suporte. Prevents: perda de estado quando um canal falha.
- (decision) Suporte automático usa base de respostas cadastradas; escalonamento humano preserva contexto e WhatsApp é canal dentro do suporte, não dependência de compra. Binds: UJ-5, suporte, privacidade. Prevents: respostas generativas erradas e compra fora do sistema.
- (decision) Internacionalização usa chaves de conteúdo e valores normalizados; idioma de exibição não altera carrinho/pedido, moeda base é EUR. Binds: catálogo, checkout, e-mails, Área da Cliente. Prevents: divergência de preço/prazo por tradução.
- (decision) Administração usa a mesma aplicação e o mesmo banco, com papéis e filas por próxima ação; não existe backoffice paralelo ou planilha como fonte de verdade. Binds: UJ-4, produção, QA, exceções. Prevents: operação manual fora do histórico do pedido.
- (assumption) Provedor de pagamento inicial: Stripe Checkout/Payment Links ou Checkout Sessions, mantendo gateway atrás de porta PaymentProvider para troca futura.
- (assumption) Provedor de e-mail inicial: Resend ou equivalente via porta EmailProvider.
- (assumption) WhatsApp inicial: Meta WhatsApp Business Cloud API ou inbox/provider compatível via porta WhatsAppProvider.
- (question) Definir posteriormente provedor final de hospedagem/infra, gateway de pagamento contratado, provedor fiscal/fatura, regras CTT/transportadora e ferramenta de atendimento humano.
- (event) Stack table tightened to contain only pinned seed technologies; provider choices such as Supabase platform, WhatsApp provider and transactional e-mail provider remain Deferred behind ports.
